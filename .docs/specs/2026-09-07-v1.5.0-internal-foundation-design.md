# v1.5.0 内部地基与工程欠账 · 设计文档

- 日期：2026-09-07
- 范围：HB-17、HB-19、HB-18、HB-20、HB-21、HB-35（执行顺序即此顺序）
- 状态：已评审通过，待实现

## 背景

v1.4.0 发布后，仓库停在一个「功能可用、地基欠账」的状态：`execCommand` 丢弃子进程输出、
终端输出散落在三个模块、prompt 层只有 21 行且把交互判定留在脚本里、两份模板内联在
`constants/index.ts`、所有子命令共享一个扁平的 `ArgvOptions`、PR 页面没有任何 CI 检查。

这些都不是缺陷——CLI 今天的行为是正确的——但它们全部会在「加第二个子命令」时变贵。
`doctor`（v2.0.0）几乎每个检查都要「跑命令读输出」，没有 HB-17 就无从做起。

## 目标与非目标

**目标**：把上述六项欠账还掉，且**不改变 CLI 任何用户可见的行为**。

**非目标**（这一版明确不做）：

- 不加任何新的 flag、新的子命令、新的输出。
- 不调整输出流向。`printWarn/printInfo/printErr` 继续走 stdout，`yocto-spinner` 继续走
  stderr。把警告改到 stderr 更符合 CLI 惯例，但那是用户可见的行为变更（重定向和管道
  拿到的内容会变），应当单独立项、单独发版说明，不能混在「只还账」的版本里。
- 不为没有调用方的 API 写实现。prompt 层只抽内核，不预先接上 `confirm`/`text`/
  `multiselect`——没有真实调用方的接口设计通常是猜的，等 v1.6.0 的 HB-12 真要用
  `confirm` 时再加，那时是几行的事。
- 不动发版流程。`release.yml` 一行不改（HB-35 是新增文件）。

## 验收标准

**现有 231 条单测 + 57 条 E2E 全绿，且 `expect(...)` 断言一处不改。**

允许随重构调整的只有两类：

1. `import` 路径与 `vi.mock()` 的目标模块——模块搬家的必然结果。
2. `vi.mock('execa')` 工厂的返回值形状——见 HB-17，这是让 mock 更贴近 execa 的真实返回。

需要改动任何一处 `expect` 才能变绿，就说明行为变了，那已经越过「不开新功能」的边界：
**停下来说明，不要顺手改断言**。这条标准之所以立得住，是因为 HB-31（2026-09-04）刚把
150 处断言收窄过一遍，现有断言足够贴身，能真正当回归保护用。

## 逐项设计

### HB-17 `execCommand` 返回执行结果

**现状**：`await execa(file, args)`，返回值直接丢弃，没有 `cwd`/`env` 选项。

**方案**：

```ts
export interface ExecOptions {
  cwd?: string
  env?: Record<string, string>
}

export interface ExecResult {
  stdout: string
  stderr: string
  exitCode: number
}

export async function execCommand(command: string, options?: ExecOptions): Promise<ExecResult>
```

两个约束是这条设计的核心：

1. **不传 `options` 时必须原样调用 `execa(file, args)`，不能传第三个参数。**
   现有测试里有 8 处 `expect(execa).toHaveBeenCalledWith('npm', ['install', ...])`，
   vitest 严格比较参数个数，多一个 `undefined` 就全红。保住这个形态不是为了将就测试，
   而是反过来——这 8 处断言从此成为「默认调用形态没被改坏」的回归保护。

2. **`allowFailure` 不下沉到这一层。** 它在 `pm.exec` 的 try/catch 里已经解决得干净；
   下沉意味着要给 execa 传 `reject: false`，又会多出第三个参数，同样打破上一条。

**mock 的调整**：`vi.mock('execa')` 现在的工厂是 `vi.fn(async () => {})`，返回 `undefined`。
一旦 `execCommand` 读取返回值就会崩，因此工厂改为返回 `{ stdout: '', stderr: '', exitCode: 0 }`。
这属于验收标准里允许的第 2 类改动，且它让 mock 比原来更接近 execa 的真实行为。

**影响面**：`src/utils/index.ts`（实现）、`tests/utils.test.ts` 与
`tests/package-manager.test.ts`（两处 mock 工厂）。调用方一处都不用改——`pm` 的三个方法
不读返回值，`git init` 也不读。

### HB-19 日志层收敛

**现状**：`printWarn/printInfo/printErr` 在 `utils/index.ts`，`yocto-spinner` 在
`package-manager.ts` 和 `commitlint-init.ts` 各自 import 一次，`main.ts` 与 `banner()`
里还有裸 `console.log`。spinner 的 start/stop/success 配对靠自觉——`uninstall` 里那段
「抛错前先 stop，否则报错和转圈抢地方」的注释就是这个纪律的手写版。

**方案**：新建 `src/utils/logger.ts`，成为终端输出的唯一出口。

- `printWarn` / `printInfo` / `printErr` 原样搬入，**流向、颜色、空行一律不动**。
- 新增 `printLine(msg)`，作为 stdout 直出的唯一出口，收掉 `main.ts`（版本号、help、
  开始/完成两行）与 `banner()` 里的裸 `console.log`。
- spinner 薄封装：导出创建函数与 `run({ start, success }, fn)` 助手，由它保证异常路径
  一定 `stop()`。`package-manager.uninstall` 里手写的 try/catch/stop 正是它要消掉的第一个。
- `yocto-spinner` 从此只在 logger 里出现一次。这与 `prompt.ts` 收敛 `@clack/prompts`
  是同一个模式，本仓库已有先例：依赖收在单一模块里，既好换也好 mock。

**不做 re-export**：`utils/index.ts` 不再转出 `print*`，调用点一次改干净。留下两条
可用路径，迟早会分叉成两种写法。

**影响面**：`utils/index.ts`（搬出 + banner 改用 printLine）、`package-manager.ts`、
`commitlint-init.ts`、`main.ts`（含转给 `bin/index.js` 的 `printErr` 那行 re-export）。
测试侧：`tests/commitlint-init.test.ts` 的 `vi.mock('@/utils')` 是**完整替换**式的
（只提供 7 个导出，不 spread actual），所以要把 `printInfo`/`printWarn` 从那份 mock 里
挪进新的 `vi.mock('@/utils/logger')`；`tests/utils.test.ts` 里 print* 的用例改 import
路径。`vi.mock('yocto-spinner')` **不用动**——logger 内部仍然 import 它，mock 照样生效。

### HB-18 prompt 内核

**现状**：`prompt.ts` 全文 21 行，`select` 的取消处理写死在 `promptLinterChoice` 里；
交互判定 `isInteractive()` 由脚本层的 `resolveLinterChoice` 自己调。

**方案**：

- 抽出 `promptSelect<T>({ message, options }): Promise<T | undefined>`，把
  「`isCancel` 判定 → `cancel(MSG.promptCancelledLabel)` → 返回 `undefined`」这个约定
  收进内核。`promptLinterChoice` 变成它上面的一层薄调用。
- 导出 `canPrompt()`（内部就是 `isInteractive()`），`resolveLinterChoice` 改调它，
  脚本层不再直接 import `isInteractive`。

**为什么不把守卫塞进 `promptLinterChoice`**：`resolveLinterChoice` 对「非交互」和
「用户取消」打印的是两条不同的消息（`MSG.noLinterNonInteractive` / `MSG.promptCancelled`）。
守卫一旦下沉，`promptLinterChoice` 就得返回一个能区分两者的三态值，签名变了，
`tests/prompt.test.ts` 的断言跟着变——违反验收标准，且换来的只是把 if 挪了个位置。

**影响面**：`prompt.ts`、`commitlint-init.ts` 的 import。`isInteractive` 本身留在
`utils/index.ts` 不动（E2E 与单测都直接用到它的语义）。

### HB-20 模板外置

**现状**：`src/constants/index.ts` 105 行，其中 100 行是两份 commitlint 模板和它们共用的
`COMMIT_TYPES` / `renderTypeEnum`。

**方案**：新建 `src/templates/commitlint.ts`，迁入两份模板与类型表；
`src/constants/index.ts` 只剩 `DEFAULT_PKG_NAME` 与 `REPO_URL`。

**`renderLintStagedConfig` 留在 `linter.ts` 不动**：它不是静态模板，而是 linter 那张
`LINTER_SPECS` 表的渲染函数——`getLintStagedCommand` 是它的输入。挪进 `templates/` 会
把一个表驱动模块劈成两半，为了「模板都在一个目录」这种整齐付出内聚的代价，不值。

**构建**：`tsdown` 的 entry 是 `src/scripts/**.ts`，新增的 `src/templates/` 和
`src/utils/logger.ts` 都不是 entry，会像 `constants`/`utils` 一样进共享 chunk 或被内联，
`tsdown.config.ts` 无需改动。注意 CLAUDE.md 已记录的那条：模板常量会被**内联进消费它的
entry**，所以任何验证脚本都不要去 `dist/` 里 grep 模板的具名导出。

**影响面**：`constants/index.ts`、`commitlint-init.ts` 的 import、
`tests/constants.test.ts`（改 import 路径，data-URL 求值那三条断言不动）。

### HB-21 `ArgvOptions` 按命令拆类型

**现状**：一个扁平 interface 装下了所有子命令的 flag，放在 `utils/index.ts` 里。

**方案**：新建 `src/types.ts`：

```ts
/** 每个子命令都接受、且由 main.ts 处理的参数 */
export interface GlobalOptions { help?: boolean, version?: boolean, clear?: boolean }

/** commitlint-init 自己的参数 */
export interface CommitlintInitOptions extends GlobalOptions { czgit?: boolean, linter?: string }

/** mri 解析出来的东西：所有子命令 flag 的并集 */
export type ParsedOptions = GlobalOptions & CommitlintInitOptions
```

`init` 的签名收窄为 `CommitlintInitOptions`；`registry.ts` 与 `main.ts` 继续用并集类型。

**为什么不把 `Script` 泛型化**：`SCRIPTS` 是异构数组，泛型化后只能写成 `Script<any>[]`，
等于没拆。而由于所有字段都是可选的，`(o: CommitlintInitOptions) => Promise<void>` 本来
就能赋给接受并集的位置（并集是 `CommitlintInitOptions` 的结构子类型），不需要泛型。

加子命令时要手工同步的只有 `ParsedOptions` 那一行——与 `SCRIPTS` 里必须加的那一项同级，
可以接受。从 `FlagSpec` 反推类型在 TS 层面能做，但要把 flag 数组改成 `as const` 并写一层
类型体操，为一个两行的收益，不做。

**影响面**：`utils/index.ts`（移出 `ArgvOptions`）、`registry.ts`、`main.ts`、
`commitlint-init.ts`。`ArgvOptions` 这个名字随之消失，改用 `ParsedOptions`。

### HB-35 PR 质量门禁 workflow

**现状**：仓库只有 `release.yml`，只在推 `v*` tag 时触发。质量门禁实际来自本地
pre-commit 钩子——绕过钩子提交的代码，在 PR 页面上看不出任何问题。

**方案**：新增 `.github/workflows/ci.yml`。

- 触发：`pull_request`，目标分支 `main` / `dev`。
- 步骤照抄 `release.yml` 已验证过的写法：`pnpm/action-setup@v6` **必须在**
  `actions/setup-node@v7` 之前（否则 `cache: pnpm` 找不到 pnpm）、`node-version: lts/*`、
  `pnpm install --frozen-lockfile`。
- 门禁四条，与 release gate 逐字一致：`pnpm typecheck` / `pnpm lint` / `pnpm test` /
  `pnpm test:e2e`。不用 `pnpm build:prod`——它要 shell 出 `nr`，而 CI 没有全局
  `@antfu/ni`。`test:e2e` 通过 globalSetup 自己构建 `dist/`，无需单独的 build 步骤。
- `concurrency` 按 PR 分组并 `cancel-in-progress`，同一个 PR 连续推送时取消旧运行。
- `permissions: contents: read`——这个 workflow 什么都不需要写。

**`release.yml` 一行不改。** 两份 workflow 里那四条命令重复，是刻意的：它们回答的是
两个不同的问题（「这个 PR 能不能合」与「这个 tag 能不能发」），合并成一个可复用 workflow
会让发版路径依赖 PR 路径的配置，代价大于省下的四行。

## 风险

| 风险 | 应对 |
|:--|:--|
| 搬迁 print* 时漏改某个调用点 | TypeScript 会直接编译失败（不做 re-export 的附带好处） |
| logger 的 spinner 封装改变了输出时序 | E2E 断言 stdout/stderr 的分流，时序变了会红 |
| `execCommand` 默认调用形态被改坏 | 8 处 `toHaveBeenCalledWith` 断言会红 |
| 六条改完后互相干扰 | 一条一个提交，每条跑 typecheck + lint + test；全部完成后跑完整 E2E |
| `ci.yml` 首次运行才发现配置错 | 它自己就是在 PR 上跑的——这个 PR 会是它的第一个用例 |

## 交付节奏

一条一个提交，顺序为 HB-17 → HB-19 → HB-18 → HB-20 → HB-21 → HB-35。
HB-17 排最前是因为它是 `doctor` 的硬前置；HB-19 紧随其后是因为它出过事
（有两个测试假通过，根因是断言挑错了流）；HB-20 / HB-21 排在后面，是为了让 v1.6.0 的
HB-14 / HB-16 有外置好的模板可改、HB-12 / HB-15 有拆好的类型可用。

六条做完后跑完整 E2E，再开 PR 到 main。
